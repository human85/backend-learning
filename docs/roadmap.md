# 后端学习路线

路线采用两轮制。第一轮优先在 30 天内形成可运行、可测试、可部署的全栈闭环；第二轮再深化复杂场景。状态只有在学习者能够解释并在当前项目中识别或使用相关知识后才提升，不以代码由谁输入作为唯一标准。

## 第一轮｜30 天 AI 辅助全栈闭环（已完成）

详细日期、里程碑和完成标准见 `docs/30-day-fullstack-loop.md`。

### 第 1 周｜NestJS、CRUD 与 PostgreSQL（已完成）

- 请求与响应生命周期
- Module、Controller、Service、依赖注入
- DTO、Pipe、异常和状态码
- 完成进程内 Projects CRUD（已完成）
- 连接 PostgreSQL，选择 ORM 并运行迁移（已完成）
- 将 Projects CRUD 从内存迁移到真实数据库（已完成）

### 第 2 周｜数据边界、认证与授权（已完成）

- 用户表、项目归属、约束和基础索引
- 注册、登录和密码哈希
- 选择并实现 Cookie、Session 或 JWT 方案
- Guard、当前用户和资源归属授权
- 用户只能访问和修改自己的项目

### 第 3 周｜前后端联调与本地工程化（已完成）

- 前端接入真实 API 和认证流程
- 统一请求错误、配置和环境变量；OpenAPI 时间盒移到首次部署闭环后补充
- 关键单元测试与 e2e
- Dockerfile 与 Compose 运行 API 和 PostgreSQL
- 使用日志定位常见请求和数据库错误

### 第 4 周｜部署与闭环验收（已完成）

- 部署 API、数据库和前端
- 生产环境变量、迁移、CORS、Cookie 与 HTTPS
- 验证注册、登录、权限和项目 CRUD
- 根据线上日志定位并修复至少一个问题
- 完成代码、安全、数据与部署清单审查

## 第二轮｜后端能力深化（进行中）

2026-09-07 起按以下阶段推进。每次只推进一个主目标；课程数是范围控制参考，不是日历承诺。当前课、复测和实际证据集中在 [学习进度](learning-progress.md)，执行方法见 [学习方法](learning-method.md)。

### R1｜收尾幂等与 Outbox 实验（已完成）

- 载体：Hono + Drizzle。框架对照最小切片、幂等 HTTP 创建与 Outbox 落库已实现。
- 第一步：先预测，再注入 Outbox 写入失败，验证普通创建及幂等创建的事务回滚和恢复后重试。
- 第二步：单 Worker 串行读取待发送事件，模拟外部接收端，成功后确认；失败保留原因并有限重试，到达上限后保留可检查的失败记录。
- 第三步：模拟“接收端已成功、事件尚未确认”的中断，证明可能重复投递，并用稳定事件 ID 在模拟接收端去重。
- 工程退出条件：成功、失败重试、重启后继续处理和重复投递场景都有可重复证据；明确单 Worker 限制，不声称多实例或恰好一次投递。
- 学习退出条件：在未给答案的场景中解释事务提交、响应丢失、外部副作用与确认的边界，并复测一次资源归属测试设计。
- 范围上限：不接真实邮件/支付，不引入 Redis、队列框架、多 Worker 领取锁、完整死信系统或新的任务查询 API。若引入已提交的 processing 状态，必须同时说明并验证其恢复方式；不能把它当作当前同步事务模型已有的问题。

R1 已达标，停止扩展这个实验，回到 Mini SaaS。完成记录的清理窗口、生产消费者可靠性进入候选项。

### R2｜把排错与基础交付能力落到 Mini SaaS（进行中，预计 3–5 次课）

- 第一课实现 Request ID 与结构化日志，后续再实现数据库 Readiness 和基础 CI。
- 日志能关联请求与错误，并避免泄露密码、Cookie、Token、连接密钥；Readiness 能反映数据库不可用。
- 基础 CI 使用隔离测试数据库，运行选定的关键测试与构建；自动生产 migration 暂不并入本阶段。
- 工程退出条件：在可恢复环境重现一次依赖故障并通过日志定位；CI 能拦住一个有意制造的关键回归；准备发布的改动部署后完成真实验收。
- 学习退出条件：学习者先判断故障层，再用证据定位，解释健康检查和日志各自不能证明什么。

### R3｜独立拆解并交付一个新需求（待开始，预计 3–5 次课）

- 载体：Mini SaaS。选一个尚未演示过的业务需求，例如项目成员邀请；示例并非已经选定或实现。
- 学习者先给出数据关系、约束、权限矩阵、API 行为和失败场景；允许查看现有代码与资料，Agent 不先给完整方案。
- Agent 根据讨论完成最小实现，学习者审查关键规则与测试；前端仅增加验收所需交互。
- 工程退出条件：适用的 migration、权限及失败测试、浏览器链路和部署验收通过。
- 学习退出条件：能发现方案中的一个边界遗漏，或独立解释一个改变条件后的故障与验证方式；记录所需提示，不以功能完成代替能力证据。

### R4｜按问题选择深化主题（待选，单主题通常 2–4 次课后复盘）

每次只从候选项选择一个有具体触发问题的主题，写下实验、衡量证据和退出条件。它不是需要全部完成的清单。

| 触发问题                 | 候选内容                                 | 可用的验收证据                         |
| ------------------------ | ---------------------------------------- | -------------------------------------- |
| 同时更新产生丢失或超额   | 事务隔离、条件更新、锁                   | 能重现竞态，修复后并发测试稳定         |
| 列表或关联查询变慢       | 关系、分页、索引、查询计划               | 使用代表性数据比较查询计划与耗时       |
| 暴力登录或重复读取       | 登录限流、Redis、缓存失效                | 验证绕过与误伤边界，或缓存正确性与收益 |
| 单 Worker 吞吐或恢复不足 | 队列、多消费者、领取与超时恢复、死信     | 并发、中断、重复和恢复实验             |
| 幂等记录增长             | 保留期限与清理                           | 明确重试窗口，并验证清理后重放语义     |
| 上线恢复缺少证据         | 备份恢复、回滚、兼容 migration、指标告警 | 隔离恢复演练、实际耗时和数据检查       |
| 出现对应业务需求         | 文件、WebSocket、异步任务、第三方服务    | 从权限与失败行为到端到端交付           |

需要独立环境或生命周期时才新增 `labs/` 或应用；不为了覆盖技术名词创建新项目。超过阶段时间盒时先审查范围，再决定缩减非关键内容或记录延长原因。

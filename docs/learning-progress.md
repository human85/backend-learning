## 当前课：R2 第一课——Request ID 与结构化日志

唯一主目标：让一次请求的 ID 能贯穿 HTTP 响应和结构化日志，支持从错误日志回到具体请求。

- 已实现：共享 `configureApp()` 在解析请求体和业务处理前注册中间件；服务端为每次请求生成 UUID，响应头 `X-Request-ID` 与请求完成 JSON 日志使用同一个编号；CORS 暴露该响应头。
- 日志只记录时间、级别、事件、请求编号、方法、路由模板、状态码、耗时；不记录原始 URL、请求体、Cookie、Token、用户标识或原始异常。异常过滤器保留显式 HTTP 4xx 合同，对未知错误返回安全 500。
- 学习证据：学习者独立答对事务回滚后重新创建 201、提交后响应丢失重放 201；正确选择公共中间件并指出每次请求应有独立编号、密码不能记录。Session 可有多个及响应头覆盖 204 由 Agent 补充，尚未独立复测。
- 当前边界：仅请求完成日志；尚未加入 Service 内部日志上下文、错误原因分类、客户端断连日志或日志存储检索系统。日志可定位失败请求，但尚不能单独定位数据库故障根因；本课未重新部署。
- 下一步：学习者审查关键 diff，解释为什么在响应完成时记录状态码，以及并发请求不能共用可变编号；再回答“同一幂等操作的两次 HTTP 重试如何编号”。结构化字段的检索价值还待独立解释。
- 本课不同时实现指标、告警、Readiness 或登录限流；R2 阶段尚未完成。

## 已知边界与后续范围

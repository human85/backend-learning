## 下一课：验证重复投递并用事件 ID 去重

唯一主目标：证明外部接收端成功但 Outbox 尚未确认时可能重复投递，并用稳定事件 ID 让接收端只产生一次副作用。

- 位置：`pending outbox_events → Worker 调用接收端成功 → 确认前中断 → pending 再投递 → 接收端按 event.id 去重 → processed`。
- 先由学习者预测中断前后 Outbox 状态、外部调用次数和业务副作用次数；Agent 等待回答后再实现故障实验。
- 工程验收：测试能稳定制造重复调用；接收端以稳定事件 ID 去重后只产生一次模拟副作用，Worker 最终能确认事件；不声称真实系统具备恰好一次投递。
- 学习验收：学习者能区分至少一次投递、重复调用和幂等副作用，并说明去重记录应由哪一方保存及其唯一键。
- 本课范围不引入 Redis、队列框架、多 Worker 领取锁、真实邮件/支付或新的任务查询 API。

## 已知边界与后续范围

- 当前 HTTP 幂等路径在一个事务内从 reservation 走到 completed；事务最终回滚不会留下该次已提交的 processing，完成记录的保留与清理是另一项策略。单独提交 reservation 的实验或未来异步领取模型才需要分析遗留 processing 的恢复。
- Hono 使用固定教学身份，不作为真实认证或生产部署样本；Worker、外部投递和幂等记录清理均未实现。
- Mini SaaS 的 Request ID、结构化日志、数据库 Readiness 与基础 CI 进入 R2；登录限流、恢复演练等缺口保留在路线图候选项中。

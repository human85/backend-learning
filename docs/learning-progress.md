## 已完成反馈：Request ID 与结构化日志

唯一主目标：让一次请求的 ID 能贯穿 HTTP 响应和结构化日志，支持从错误日志回到具体请求。

- 已实现：共享 `configureApp()` 在解析请求体和业务处理前注册中间件；服务端为每次请求生成 UUID，响应头 `X-Request-ID` 与请求完成 JSON 日志使用同一个编号；CORS 暴露该响应头。
- 日志只记录时间、级别、事件、请求编号、方法、路由模板、状态码、耗时；不记录原始 URL、请求体、Cookie、Token、用户标识或原始异常。异常过滤器保留显式 HTTP 4xx 合同，对未知错误返回安全 500。
- 学习证据：学习者独立答对事务回滚后重新创建 201、提交后响应丢失重放 201；正确选择公共中间件并指出每次请求应有独立编号、密码不能记录。Session 可有多个及响应头覆盖 204 由 Agent 补充，尚未独立复测。
- 当前边界：仅请求完成日志；尚未加入 Service 内部日志上下文、错误原因分类、客户端断连日志或日志存储检索系统。日志可定位失败请求，但尚不能单独定位数据库故障根因；本课未重新部署。
- 实现审查证据：学习者正确指出提前写日志会记录错误状态码；正确预测全局编号会让 A 使用 B 的编号，并解释每次函数调用创建局部编号可避免干扰。
- 迁移回答：学习者答对两次重试 Request ID 不同、Idempotency-Key 相同，并说明是新的请求；幂等键关联同一逻辑操作的排错作用由 Agent 补充。
- 日志检索证据：学习者正确选择 statusCode、durationMs 筛选失败慢请求，并用 Request ID 关联；限定创建接口还需 method 和 route，由 Agent 补充，后续间隔复测。
- 后续间隔复测 Session、幂等键职责及完整日志筛选条件；需要 Agent 补充的部分不算全面独立掌握。

## 当前课：数据库 Readiness

- 唯一目标：数据库不可用时 `/ready` 有界返回 503，资源不因重复探测堆积；`/health` 保持静态存活检查。
- 学习证据：学习者判断 HTTP 可响应不代表数据库连接正常；提出最大等待时长，并正确说明 Promise.race 不取消底层查询、重复探测增加数据库压力。最初选择失败返回 500，503 语义及“HTTP 可响应不证明整个 Service 正常”由 Agent 补充。
- 工程证据：专用 pg 池 max=1、并发共享一次探测；连接等待 1000ms、服务端语句 500ms、客户端查询 750ms，失败连接销毁、成功连接释放复用，应用关闭时结束探测池。
- HTTP 成功返回 200 和 `{ status: 'ok' }`，失败返回 503 和 `{ status: 'not_ready' }`，响应禁止缓存；失败完成日志通过 Request ID 关联安全的 database_probe_failed 分类，不暴露原始数据库错误。
- 实验：本机 mini_saas_test 经测试专属 TCP 代理执行 200 → 503 → 200；握手无响应、已建立连接停止转发时请求均在测试上限内返回，重复并发失败后代理连接清零；真实 pg_sleep 被服务端 statement_timeout 取消。把失败连接改为复用时单元测试失败，恢复后通过。故障操作由 Agent 演示，未作为学习者独立测评。
- 边界：仅证明独立连接可执行 SELECT 1，不检查业务池饱和、表结构、写权限或全部业务能力；连接与查询是两个阶段，预算合计约 1750ms 加调度开销，并非严格实时总截止时间。应用启动仍依赖 TypeORM 建连；没有修改部署平台探测配置或重新部署。
- 实现审查：学习者能预测复用查询超时的连接会让后续请求超时；`/ready` 为 200 仍不能证明业务创建成功的迁移题暂未作答，已提示其不覆盖连接池、schema、权限、输入与写入/事务。
- Readiness 迁移证据：学习者将 409 Email is already registered 判断为业务规则拒绝，并优先查看请求日志；能指出提示与项目创建不符。Agent 补充日志不记录请求参数，需用 Request ID 核对 method、route、statusCode，再查看浏览器 Network 的实际响应；/ready=200 只能排除本次独立数据库探测失败。
- 当前课：基础 CI。工作流已在 push 与 pull request 触发，使用独立 PostgreSQL 17 服务和 CI 注入的测试环境变量；依次执行锁文件安装、格式、只读 lint、单元测试、migration、HTTP e2e、build 与无重写检查。
- 故障证据：学习者最初选择单元测试；Agent 补充 DTO 校验须由 HTTP e2e 覆盖。临时删除 RegisterDto 的密码最小长度后，/auth/register 短密码用例实际得到 201 而非预期 400，34 项应用 e2e 中 1 项失败；恢复后 34 项重新通过。
- 远端证据：首次 GitHub runner 在 HTTP e2e 阶段发现 readiness e2e 隐式读取本机文件；修复为 CI DATABASE_URL 优先、本地文件回退后，[GitHub Actions run 34202748980](https://github.com/human85/backend-learning/actions/runs/34202748980) 在 59 秒内完整通过。
- 当前边界：它不运行 Hono 会清表的集成测试、前端测试、浏览器/线上验收或自动生产 migration。CI 的测试数据库只用于该 job，不能代替部署验证。
- CI 审查证据：学习者独立说明 migration 先于 e2e 是因为否则数据库仍是旧 schema，测试无法代表当前代码；并说明云端 CI 不能读取本机环境变量。Agent 补充 CI 新库可能为空，migration 负责建立当前 schema（必要时也可包含受控数据迁移）。
- R2 退出判断：学习者能说明 CI、`/ready`、Request ID 和业务验收的基本分工；把“CI 证明数据连接没问题”和“ready 证明服务正常”说得过宽，Agent 收窄为临时数据库上的选定测试、当前一次 SELECT 1 探测。Request ID 用于找到对应请求的回答正确。
- 当前边界：R2 工程退出还缺准备发布改动的部署后真实验收；当前没有将本轮变更重新部署到 Render，也不能把历史线上验收当作本次证据。
- 部署验收预测：学习者提出先检查 `/health`、`/ready`，再做 e2e 测试并用 Request ID 找到对应请求；Agent 收窄为生产只做可清理的 smoke test，完整 e2e 留在 CI 隔离数据库，避免清表测试破坏生产数据。
- Smoke test 清理反馈：学习者提出统一使用 test/temp 命名并在结束后清理，删除失败时根据响应定位代码逻辑；方向正确但需唯一标记、`finally` 清理、数据库状态核对和 Request ID 日志证据。固定名称可能撞击真实数据，响应本身也不等于根因。
- 清理顺序复测：学习者回答项目 → 账号 → Session，并要求前一项完成后再进入下一项。项目优先正确；当前 `projects.owner_id` 是 `ON DELETE RESTRICT`，Session 表没有用户外键，因此语义上应先项目、再注销/销毁 Session、最后删除账号。若一步失败，不应短路后续独立清理，应收集各步错误并最终报告。
- 孤儿数据反馈：学习者提出删除没有对应用户的项目；Agent 补充当前外键会阻止账号先删，若外键被绕过也只能按本次保存的临时项目 ID 定向补偿，不能全库删除所有孤儿项目，以免误删其他故障数据。
- 删除失败复测：学习者先选择查看日志；方向正确但还需使用响应 Request ID 核对 DELETE 路由、状态码、耗时和认证用户，并查询该 projectId 的实际存在与归属后再重试。
- 删除重试证据复测：学习者能独立列出通过 Request ID 查找日志，并核对 method、statusCode、duration、timestamp；Agent 补充 route、认证用户和数据库 projectId/归属状态，作为避免误删的完整证据集。
- Smoke test 清理验收复测：学习者指出需确认项目、用户和 Session 都清理完毕。Agent 补充不能只看 204，应按保存的 ID/唯一标记查询数据库，并核对清理前后的 Session 数量；当前应用没有公开删除用户 API，用户清理若需执行必须使用受控的数据库管理操作。
- 清理证据复测：学习者正确判断仅有 204、无法查询数据库时不能标记清理成功，因为响应状态不能完全代表数据库真实状态；应标记为未验证并保留待查证据。
- 线上版本证据复测：学习者正确判断部署平台显示成功、`/health` 和 `/ready` 正常仍不够；若无法确认线上实例对应本次 commit，smoke test 结果无法归因于当前改动，因此应先核对部署版本或 commit SHA。
- Smoke 清理失败处置复测：学习者正确判断业务接口全部成功但数据库仍有临时 Session 时不能标记 smoke 通过；应查询数据库并定向清理残留脏数据，再次核对结果。
- Smoke 失败与最终状态复测：学习者把第一次 DELETE 返回 500、后续清理成功判断为整体通过；该回答只覆盖最终资源状态，未覆盖请求合同和未解释的失败。需间隔复测“最终状态正确”与“每次关键请求成功”是两条独立验收条件。
- Smoke 失败记录保留复测：学习者正确判断修复后的成功不能覆盖第一次失败，应保留失败原因和 Request ID，以便后续故障排查；最终报告需分开描述失败运行与修复后的通过运行。
- DELETE 404 排查链路复测：学习者正确选择通过 Request ID 找到日志，核对 route、statusCode、method 等，再定位问题并检查代码；需结合保存的 projectId、认证用户和数据库实际归属区分传错 ID 与 Service/路由 bug。
- 修复后完整回归复测：学习者正确判断 DELETE 修复后应先跑相关测试，再完整执行 smoke，因为局部改动可能影响认证、Session、归属和清理链路的其他步骤。
- R2 退出条件复测：学习者正确判断仅有本地测试和 CI 通过仍不能完成 R2，因为缺少真实环境验证；还需目标版本、健康/就绪、可清理业务 smoke、Request ID 日志和数据库清理核对证据。
- 配置证据复测：学习者正确判断不能打印完整配置以免泄露；但“数据库连接成功即配置正确”只适用于 `DATABASE_URL` 的连通与认证，不覆盖 `SESSION_SECRET`、`FRONTEND_ORIGIN` 等配置，需按各自生效链路验证。
- 配置 fail-fast 复测：学习者正确判断 `SESSION_SECRET` 缺失或不合规时应在启动阶段失败，而不是启动后让登录请求必然返回 500；理由是避免浪费资源和错误流量。错误输出仍不得暴露密钥值。
- DELETE 重试复测：学习者判断响应丢失后的同一 DELETE 具备安全、幂等；幂等部分正确，Agent 补充 HTTP safe 与 idempotent 不同。DELETE 会改变状态，因此不是 safe method；当前实现首次返回 204、重复返回 404，但资源最终不存在，状态效果仍幂等。
- 幂等复述证据：学习者独立说明幂等关注最终资源状态，两次 DELETE 后资源都不存在；响应码反映具体请求状态，不必保持相同。该复述准确覆盖状态效果与响应合同的区别。

# 第一轮生产检查总结

## 已验证的闭环

- 外部输入经过 DTO 与运行时 ValidationPipe。
- PostgreSQL 使用 migration、主键、唯一约束、外键和资源归属条件。
- 密码使用 Argon2id；Session 保存于 PostgreSQL，Cookie 使用 HttpOnly、SameSite=Lax 和生产 Secure。
- 未登录、错误输入、资源不存在和跨用户访问具有明确响应。
- Service 单元测试、HTTP e2e、OpenAPI 契约测试和真实线上请求共同提供证据。
- API 与 PostgreSQL 可通过 Docker Compose 运行；Render、Neon 和静态前端已完成真实部署。
- 能按代码/构建、运行配置、数据库、HTTP 边缘和浏览器层定位常见故障。

## 恢复方式不能混用

- 代码缺陷且 schema 兼容：回滚应用 Image。
- 环境变量错误：恢复配置并重启应用。
- schema 不兼容但数据仍在：优先通过兼容代码或修复 migration 向前恢复。
- 数据被删除或覆盖：先恢复备份到新数据库并验证，再精确修复或切换；避免直接覆盖当前生产数据。

RPO 表示最多可接受丢失多少数据，RTO 表示最多可接受中断多久。存在备份不等于具备恢复能力，必须通过恢复演练验证。

## 健康与可观测性边界

- Liveness 证明进程存活。
- Readiness 证明当前具备处理业务请求的依赖条件；依赖不可用通常返回 `503`。
- 日志解释单次事件，指标描述趋势，告警负责通知。
- 数据库可连接不等于业务数据正确；逻辑删除需要审计日志、业务指标或数据一致性检查发现。

## 已知未实现项

- 登录或通用 API 限流。
- Request ID 与结构化日志。
- 指标、告警和数据库 Readiness。
- Neon 备份的真实恢复演练与明确 RPO/RTO。
- 自动化生产 migration、正式回滚演练和容量测试。

这些是第二轮深化清单，不影响第一轮“完成最小全栈交付闭环”的结论，也不能被描述成已经具备的生产能力。

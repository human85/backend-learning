# migration、回填与兼容发布

> 2026-11-10 整理。以下是概念课示例，没有在项目数据库执行；Mini SaaS 实际仍使用 `name` 字段。

## 为什么分阶段

发布时，新旧实例可能短暂共存。代码回退也可能重新引入旧版本，所以数据库变更必须考虑所有读取方和写入方。前端可类比 API 字段升级：新客户端发布，不代表旧客户端已经消失；数据库还多了历史数据和约束的要求。

Entity 是代码中的映射；数据库实际结构通过 migration 更新。新 Entity 查询不存在的列可能报错，即使字段声明允许为空也不能避免。当前迁移配置在 `apps/mini-saas/src/database/`，写入逻辑在 `apps/mini-saas/src/projects/projects.service.ts`。

## 示例：name 改为 title

1. 新增允许为空的 `title`，保留 `name`。
2. 部署过渡版本：读 `name`，创建与更新时同时写两个字段。两个字段应由同一条 SQL 或同一事务更新。
3. 确认所有只写 `name` 的旧实例、任务、脚本退出，再以 `name` 为准回填并核对差异。
4. 发布读取 `title` 的版本，暂时维持双写以保留回退条件。对外 API 字段是否改名是另一个合同变更，不能混为一谈。
5. 不再需要回退到依赖旧列的版本后，发布彻底不读写 `name` 的版本，包括移除 ORM 映射；确认使用方都已退出，再删除旧列。

这些阶段不能不加区分地放入同一次发布前的 migration 命令；迁移文件执行顺序不能替代应用版本切换和实例退出证据。

## 回填就是更新已有记录

在第 3 步，核心 SQL 为：

```sql
UPDATE projects
SET title = name
WHERE title IS DISTINCT FROM name;
```

每一行使用自身的 `name`，不仅修正 NULL，也修正旧实例单写产生的非空差异。只有已确定 `name` 仍是权威来源时，才能按此方向覆盖。

小表可用单独的数据 migration；大表可用独立脚本每批更新一部分，每批独立提交，观察耗时与负载后继续。若所有批次仍放在同一大事务，锁不能逐批释放。批量上限不等于查询扫描成本有界；生产规模还需评估索引、扫描方式、锁和节奏。

验收可查询 `SELECT count(*) FROM projects WHERE title IS DISTINCT FROM name;`，结果为 0 还需所有写入方持续保持一致。只做一次回填不能防止之后的旧写入再次制造差异。

## 默认值、约束和回退

- DEFAULT 用于省略字段或显式使用 DEFAULT 的插入，不会替换显式 NULL；SET DEFAULT 不会补齐已有 NULL。
- 增加 NOT NULL 前，已有数据和所有后续写入方都要满足要求。
- 删除列会丢失该列数据；本例若 title 保留完整名称，可重建 name 并从 title 回填，但并非直接回滚代码即可恢复。没有其他副本的数据需要备份等恢复途径。
- 永久双写增加维护成本：难以确定权威字段，新增写入路径容易漏写，也增加数据存储与更新开销。

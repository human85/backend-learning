# 限流、幂等与异步任务可靠性

## 限流和重试

- 登录接口通常同时按 IP 和账号/邮箱限流：只按 IP 会误伤共享网络，也能被换 IP 绕过；只按账号会被用来锁定目标账号。
- 超过频率限制返回 `429 Too Many Requests`，可以用 `Retry-After` 告知重试时间。
- 客户端应使用指数退避、抖动和最大重试次数，避免重试风暴。临时网络/数据库故障可以重试，永久格式错误不应无限重试。
- 密码、完整 Cookie、Session ID、JWT 和 `Authorization` 不能写入日志。详细错误放在服务端日志，响应只返回稳定的错误码、通用消息和 `requestId`。

## 幂等键

网络超时只说明客户端没有收到响应，不说明服务端没有执行。对于可能重复的创建或增量操作，客户端为一次逻辑操作生成一个幂等键，并在重试时复用它。

服务端应先完成认证，再用一个隔离范围查找幂等记录，常见范围是：

```text
userId + operation + idempotencyKey
```

记录还可以保存请求哈希、处理状态和原始响应：相同 key 与相同哈希返回原结果；相同 key 但不同内容则拒绝，避免把一次操作的结果错误地返回给另一种请求。幂等记录应放在数据库或共享 Redis 中，并保留足够长的重试窗口；过早删除会让迟到重试重新执行。

并发请求不能只做“先查询、再插入”，因为两个请求可能同时看到不存在。数据库联合唯一约束或 Redis 原子 `SET NX` 才能仲裁竞争。

本仓库的 Hono 小实验用 `idempotency_records` 保存 `processing`/`completed` 状态、请求哈希和原始响应，并用：

```sql
CREATE UNIQUE INDEX idempotency_records_scope_unique
ON idempotency_records (user_id, operation, idempotency_key);
```

插入时使用 `ON CONFLICT DO NOTHING`，拿到插入结果的请求获得 reservation；没有插入的请求再读取已有记录，按哈希返回重放、错误复用冲突或处理中状态。真实数据库集成测试验证了两个并发请求只产生一条记录。

在当前 Hono 的 `POST /projects` 中，reservation、项目插入、Outbox 事件和原始 `201` 响应处于同一个 PostgreSQL 事务。竞争请求的唯一约束检查可能等待另一个事务结束；先请求提交后，后请求可读取 completed 并重放。如果先请求回滚，后请求可获得 reservation。等待期间的超时与已提交 processing 的恢复是不同问题。

### 三种情况必须分开

| 情况                             | 持久化边界                                                            | 恢复或清理问题                                                                       |
| -------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 当前 HTTP 同步事务               | reservation 到 completed 在一个事务内；最终回滚时本次业务写入全部取消 | 提交成功但 HTTP 响应丢失时用同 key 重放；不能假定进程中断必然留下已提交的 processing |
| 单独提交 reservation，随后再处理 | processing 已经提交，后续进程可能失败                                 | 需要超时识别、恢复/接管和避免旧执行者重复完成；这是不同模型，当前 HTTP 路径未采用    |
| 已完成幂等记录长期保留           | completed 与原响应已经提交                                            | 先定义重试窗口，再设计清理；删除后旧 key 可能被当作新请求                            |

Repository 原语测试曾独立调用 reserve，因此能产生持久化的 processing；不能把这个测试行为直接套到 HTTP 事务。未来 Worker 若先提交领取状态再发送，也需要单独分析领取超时和恢复，不能与 HTTP reservation 混用。

进程中断后连接尚未被数据库判定断开时，事务可能暂时占用连接或锁；这不等于已提交了半条业务记录。客户端看到超时也不能判断提交结果。以上模型按当前 [幂等编排代码](../../apps/hono-drizzle/src/idempotency/idempotent-projects.service.ts) 与 [PostgreSQL 事务语义](https://www.postgresql.org/docs/current/tutorial-transactions.html) 于 2026-09-07 核对；尚未通过本仓库的故障注入实验验证全部场景。

## 事务性 Outbox

数据库事务不能回滚已经发送给邮件、支付等外部服务的请求。把业务资源和一条 outbox 事件放在同一个数据库事务中：事务回滚时没有事件，提交后 Worker 可以可靠地重试发送。

当前 Hono 实验的项目创建 Service 会在写入项目后插入 `outbox_events` 的 `pending` 行，再提交事务；普通创建和幂等创建都复用这个事务边界。这里的“写入成功”只代表事件已经可靠保存，不代表邮件等外部副作用已经完成，后续仍需要 Worker 领取并更新事件状态。

当前集成测试覆盖成功写入与重试，但尚未注入 Outbox 写入失败来验证整体回滚。该实验是下一课目标，不写成已有验证。R1 只实现单 Worker、模拟接收端、有限重试与重复投递实验，详细范围见 [路线图](../roadmap.md)。

Worker 应在处理成功后确认消息。先确认再处理会丢消息；处理后确认则可能在“副作用已完成、确认尚未提交”时重复投递，因此消费者和外部服务也要使用幂等键。对于连续失败的消息，限制重试次数后放入死信队列，保留原因并支持修复后重新投递。

## 异步 HTTP 状态

- `201 Created` 表示主资源已经创建，不必等待附带的邮件等异步副作用完成。
- `202 Accepted` 表示请求已接受但任务尚未完成，响应应提供 `jobId` 或 `Location`。
- 查询任务状态本身成功时返回 `200`；任务的业务状态可以是 `pending`、`running`、`succeeded` 或 `failed`。查询失败才使用 `5xx`。
- 任务查询必须使用服务端 Session/JWT 得到的 `userId` 过滤，不能只按客户端提供的任务 ID 查询。

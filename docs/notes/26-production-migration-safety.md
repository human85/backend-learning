# 生产 migration 安全

## 为什么代码回滚不够

应用代码与数据库 schema 独立变化。破坏性 migration 已删除或改名字段后，只把应用回滚到旧版本，旧 SQL 仍会因为列不存在而失败。TypeORM 返回的不是缺少属性的对象，而是 PostgreSQL 查询错误。

## 扩展—迁移—收缩

以 `projects.name` 改为 `projects.title` 为例：

1. 扩展：新增暂时允许 `NULL` 的 `title`，保留 `name`。
2. 兼容：部署能读取两个字段并在过渡期双写的代码。
3. 回填：将历史 `name` 写入 `title`，验证没有遗漏。
4. 切换：增加 `NOT NULL` 等目标约束，部署只使用 `title` 的代码。
5. 收缩：确认旧版本不会再运行后，单独删除 `name`。

给已有数据表直接添加没有默认值的 `NOT NULL` 列会失败，因为所有历史行在新增时都会得到 `NULL`；空表没有历史行违反约束，因此是不同边界。

## 恢复层次

- 首选通过兼容 schema 让新旧代码都可运行。
- 已发生问题时优先用修复 migration 向前恢复。
- 能从现有数据或业务来源重建时执行精确回填。
- 只有数据不可重建时才使用经过验证的备份恢复，并评估恢复点之后的数据损失。

`down()` 能重新创建列结构，但不能凭空恢复已经删除的列数据。

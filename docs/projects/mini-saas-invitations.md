# Mini SaaS：项目邀请、转让与退出

> 2026-11-18，后端邀请、成员只读、转让/退出和成员名单已在 feat/project-member-read-access 验证；前端协作主链路已通过本地桌面与移动浏览器验收。部署及目标环境迁移仍待完成。

## 已确认范围与规则

- 仅项目，不新增组织；邀请已注册用户，通过应用内页面接受或拒绝，不接邮件或过期机制。
- 所有者可改名、删除、邀请及转让；普通成员只读，可自行退出。陌生用户不能读取项目。
- 所有者先转让给现有成员，自己成为普通成员，然后可以自行退出。转让不自动退出、不删除项目。
- 所有者只保存在 projects.owner_id，不同时作为普通成员保存在成员表。
- 成员表记录当前成员关系，同项目/用户不能重复；邀请表记录历史，不能替代当前权限检查。
- 当前已是成员时拒绝发起邀请；同项目/受邀人最多一条 pending。重新邀请新增记录，保留历史。
- 接受邀请必须匹配 Session 用户，首次接受必须为 pending；邀请状态与成员新增在同一事务完成。
- 重复接受：已接受且仍是成员时返回已接受，不重复写入；已退出时旧邀请不能恢复成员，需新邀请。
- 发起邀请及转让时，使用 Session 身份检查当前所有者，不信任客户端 inviterId/ownerId。
- 学习者确认删除项目时同时删除成员关系和邀请记录，用户记录保留。
- 学习者确认所有权转让后，旧所有者此前发出的 pending 邀请继续有效，授权属于项目；inviter_id 仅记录当时邀请人。

## 数据结构建议

| 表              | 字段与约束                                                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| projects        | 继续使用 owner_id；保留现有用户外键                                                                                  |
| project_members | id、project_id、member_id；两外键非空；联合唯一 (project_id, member_id)                                              |
| invitations     | id、project_id、inviter_id、invitee_id、status；必要外键与状态检查；pending 的 (project_id, invitee_id) 部分唯一索引 |

InvitationEntity 已包含 created_at；项目外键采用 CASCADE，用户外键采用 RESTRICT。客户端不得直接提交身份、状态或归属字段。不能把外键存在性等同于邀请权限，所有者/成员排斥规则仍需 Service 维护。

## 已实现接口与前端接入

创建邀请、收到邀请列表、接受/拒绝、转让和退出已实现。项目列表、详情和成员名单为所有者或当前成员可读，管理仍仅限所有者。邀请列表不支持查询参数、返回全部本人各状态记录并按 id 倒序；暂无分页，额外参数为 400，响应 no-store。接受/拒绝和退出无业务 body/query，额外字段为 400；转让仅接收目标用户 memberId，不能提交 ownerId 等身份字段。

成员名单以一次 SQL 查询同时按 Session 核对访问资格并读取当前角色。200 响应只返回 userId 和 role，所有者在首位，普通成员按用户 ID 升序排列。转让下拉框筛选 role 为 member 的记录，将 userId 传给转让接口的 memberId。未登录为 401，项目不存在或没有当前项目身份为 404，非法路径 ID 或额外查询参数为 400。响应使用 no-store。

| 行为          | 路径建议                                        | 结果建议                                              |
| ------------- | ----------------------------------------------- | ----------------------------------------------------- |
| 创建邀请      | POST /projects/:id/invitations，body: inviteeId | 201；重复 pending、已是成员或邀请自己为 409           |
| 收到的邀请    | GET /invitations                                | 200；只查 Session 用户收到的记录                      |
| 接受          | POST /invitations/:id/accept                    | 200；已接受且仍有访问身份时返回已接受；不恢复已退出者 |
| 拒绝          | POST /invitations/:id/reject                    | 204；pending 可拒绝，其他状态按冲突处理               |
| 成员列表      | GET /projects/:id/members                       | 200；项目所有者/成员可查，为转让选择成员提供入口      |
| 转让          | POST /projects/:id/transfer，body: memberId     | 204；仅当前所有者，可转给当前普通成员                 |
| 退出          | DELETE /projects/:id/members/me                 | 204；所有者直接退出为 409                             |
| 项目列表/详情 | 沿用 GET /projects 与 GET /projects/:id         | 扩展为自有及加入的项目；PATCH/DELETE 仍仅限所有者     |

未登录为 401；输入非法为 400；不存在或无权操作的资源沿用现有项目的 404 隐藏策略；业务状态冲突为 409。路径、响应 DTO 和具体错误码在实现时统一，不能复用一个过宽的“能读取项目”检查来授权修改。

前端已实现项目工作区与邀请收件箱。TanStack Query 使用 `['collaboration', userId, ...]` 作用域：项目列表按用户隔离，成员名单再附加 projectId，邀请列表按用户隔离。登录和退出时清理这些缓存，并通知同源标签页重新验证 Session。项目列表与名单的所有者一致时才展示管理或退出操作。创建刷新项目；接受刷新邀请、项目和对应名单；拒绝刷新邀请；改名刷新项目；转让刷新项目与名单；退出或删除成功后先从当前缓存移除项目，再刷新列表，并把旧名单缓存标为失效且本次不自动重取。删除项目时后端级联清理成员和邀请，前端同时刷新邀请。响应结果不明确时会重新读取受影响的数据。

真实浏览器验收使用 Playwright Chrome、本地隔离 PostgreSQL 17，并先执行从零 migration。以桌面 `1280 CSS px` 与移动 `390 CSS px` 两个会话覆盖项目创建/改名、首次邀请拒绝、历史后重邀及接受、成员名单与所有者/成员控件、转让、退出、账号切换和项目删除级联。转让在原所有者页面立即反映；另一个 Chrome 会话需要手动刷新后才能看到新角色。没有实时跨会话推送，线上环境尚未参与。

## 事务与锁建议

创建、接受、拒绝、转让和退出已实现下述协议及 2 秒 lock_timeout。接受/拒绝共用 lockReceived：先读取本人邀请以定位项目，拿到项目锁后按邀请 ID/项目/受邀人重新查询并锁定邀请。转让按当前 owner 加锁项目，再锁目标成员；退出初步定位可访问项目，拿到项目锁后重新检查 owner 和实际 DELETE 的成员匹配结果。

采用 PostgreSQL READ COMMITTED。把项目行作为同一项目授权变更的共同锁入口：

```sql
BEGIN;
SELECT id, owner_id FROM projects WHERE id = $1 FOR UPDATE;
-- 拿到锁后再检查身份、邀请状态及当前成员关系，完成写入。
COMMIT;
```

这是事务结构示意，不是可直接运行的完整业务 SQL。锁住的是匹配到的项目行，不是整个项目相关数据；不存在的行不会被锁住。项目锁不会自动阻止别人直接删除成员记录，依赖所有相关写入路径遵守协议。

- 发邀请、接受/拒绝、转让、退出和删除项目都先取得项目锁，再读取/修改邀请和成员；避免一条路径先锁邀请、另一条先锁项目。
- 接受时 invitationId 对应的 projectId 必须从数据库获取；在锁住项目后重新查询并检查邀请，不能信任客户端或锁前的旧状态。
- 转让时再次核对 owner_id 与 Session 用户匹配，确认接收者仍是成员；条件更新 owner_id，检查影响一行，删除新所有者成员记录并检查结果，再插入原所有者成员记录；任一步失败整体回滚。
- 退出时拿到项目锁后重新检查是否已变为所有者。若转让先提交，接收者已经是所有者，不能继续按旧成员身份退出；若退出先提交，转让应发现目标成员不存在并拒绝。
- 唯一约束仍作数据库兜底；事务内所有查询/写入使用该事务 manager。锁持有期间不等待页面操作或外部网络请求；实现时给锁等待设置合理上限并映射安全错误。

普通 SELECT 通常不会被该行锁阻塞，其他项目可独立处理。事务提交或回滚释放锁。参考 [PostgreSQL 17 显式锁文档](https://www.postgresql.org/docs/17/explicit-locking.html)。

- 输入/身份：拒绝伪造 inviterId、非法 ID/额外字段；未登录；不能列出或处理别人的邀请；普通成员不可邀请、改名、删除、转让。
- 唯一性：重复成员、重复 pending、已是成员邀请；接受/拒绝/退出后允许符合规则的新邀请，历史不被重置。
- 原子性：接受时成员写入失败，pending 保留；转让中途失败，owner 与所有成员记录恢复原状。
- 重试：并发接受只新增一个成员，已接受重试成功；退出后旧邀请不能重建成员关系。
- 转让：旧所有者变普通成员、新所有者不重复存在于成员表、其他成员不变；非成员目标、自转让、过时所有者请求均不改数据。
- 真实数据库并发：用两个连接控制转让/退出的两种先后顺序，验证等待、提交、失败回滚后的重新检查与锁释放；验证不同项目不共用同一行锁。假 manager 测试不能替代这些证据。
- 集成/交付：migration 与真实约束、HTTP 权限矩阵、浏览器邀请/转让/退出链路均已有本地证据。合入与发布仍需先确认目标 schema、自动部署触发和 migration 顺序，再针对目标版本做可清理 smoke，核对日志与数据库最终状态；本地浏览器通过不能记为生产可用。

## 已确定的删除和重试边界

- 项目删除已确认级联删除成员/邀请，用户引用采用 RESTRICT；不声称邀请历史是永久审计。未来若新增用户删除功能需另定清理合同。
- 转让前 pending 继续有效已确认；接受时已是所有者且邀请 accepted，按已有访问身份返回 200，不插入普通成员记录。
- 拒绝的重复请求为 409，退出的重复请求为 404；转让后旧 owner 重试转让因不再拥有项目返回 404，不代表第一次未成功，客户端需结合当前状态确认。
- 这些是待定合同，不把尚未确认的取舍写成学习者已决定；当前下一步以学习快照为准。
